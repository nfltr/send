# Performance notes

One line per change that moved nfltr-send's throughput, newest first:
what changed, the measurement, and what keeps it. Measure old and new
interleaved on the same machine and report medians.

| change | measured | kept by |
|---|---|---|
| The sender's root and outboard are built on every core: each 256 KiB chunk's chaining value GOMAXPROCS at a time, as the receiver's from-disk check does, the parents above them on one core (`internal/xfer/verified` `New`); github.com/nfltr/blake3 v1.5.0 | darwin/arm64 (Apple M5, 10 cores), loopback through a local relay, load average 30-42, 6 runs each interleaved, medians for one 1 GiB file, v0.1.0 (9a8f7d1), NEON only (60d01cc) and this (5469b75): sender start to address 1.47, 0.72 and 0.15 s; address to received 5.29, 4.55 and 4.68 s; sender start to receiver exit 6.79, 5.26 and 4.82 s. `verified.New` alone on the cached file (load 29): 1.30, 0.60 and 0.098 s | `TestNewMatchesSequential` (root and outboard equal bao.Encode's around chunk, 16 KiB and subtree boundaries) |
| BLAKE3 and Bao on arm64 run NEON assembly: github.com/nfltr/blake3, lukechampine.com/blake3 v1.4.1 plus a 4-lane chunk and parent compression (`internal/xfer/verified`) | darwin/arm64 (Apple M5), loopback through a local relay, load average 12-16, 6 runs each interleaved, medians before and after: 1 GiB sender start (root and outboard) 1.54 s and 0.73 s, the receiver's from-disk check 0.28 s and 0.12 s, receiver wall 5.16 s and 5.15 s (the transfer is bound by the network path, not the per-chunk checks), send to received 6.71 s and 6.03 s, receiver CPU 13.5 s and 11.1 s; 10,000 x 4 KiB unchanged (2.66 s and 2.58 s). One core compresses 16 KiB in 7.7 us instead of 18.2 us | the fork's `TestCompressBufferDifferential`, `TestMergeSubtreesDifferential` (v1.5.0), `FuzzCompressBuffer` and BLAKE3 test vectors; `BenchmarkTransfer` |
| Small files and resume. The received files are synced once before the commit, not one drive flush each (macOS: `fsync` per file, the intent's `F_FULLFSYNC` flushes the drive once; Linux: one `syncfs`; `internal/xfer/sync_*.go`); a one-chunk file keeps no tree file (`keptTree`); the receiver exits without waiting for the direct path's drain (`cmd/nfltr-send` `receive`); a resume sends only the chunks missing or not verifying (protocol 4, `need`) | Loopback through a local relay, darwin/arm64, load average 7-20, 6 runs each interleaved, wall medians before and after: 10,000 x 4 KiB 49.7 s and 1.8 s; 1 GiB 4.9 s and 4.0 s; 100 x 10 MiB + 1,000 x 1-64 KiB 10.3 s and 4.4 s; 1 MiB 1.13 s and 0.11 s. 1 GiB cut at 512 MiB, 4 KiB of the part overwritten at 100 MiB: the resume wrote 969 MB before, one chunk plus the missing half after | `TestSmallFilesResumeWithoutKeptTrees`, `TestResumeSendsOnlyTheBadChunk`; spec `Minimal` (mutant `resend-verified`) |
| Verified streaming (BLAKE3 root, Bao outboard). The receiver verifies up to 8 arriving chunks at once while it reads the next frames, each read straight into its own buffer (`internal/xfer/receive.go` `run`, `inFlight`); the from-disk check verifies the file's 256 KiB chunks in parallel across GOMAXPROCS (`internal/xfer/verified` `Verify`); the sender no longer hashes what it sends and writes each data frame, header and chunk read in place, in one write (`internal/xfer/send.go` `sendFile`, `writeFrame`) | `BenchmarkTransfer` (64 MiB over a pipe), darwin/arm64, 10 cores, load average 8-9, 16 runs each interleaved: SHA-256 version median 754 MB/s, this one 884 MB/s; under background QoS (`taskpolicy -b`, efficiency cores) 371 and 382 MB/s. Verifying each chunk in line and hashing the file on one core afterwards measured half the SHA-256 version: the library has no arm64 assembly, so one core hashes a chunk at about 435 MB/s. 2 or 4 workers for the from-disk check measured below GOMAXPROCS | `BenchmarkTransfer`; `TestVerify` (parallel check, first bad chunk) |
